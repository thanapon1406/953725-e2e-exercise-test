1. ถ้า test fail ที่ 4.2.5 เราจะรู้ได้อย่างไรว่า bug อยู่ที่ route, service, repository หรือ test data
ตอบ. ไม่สามารถเช็คได้ว่า bug อยู่ที่ไหนต้องไล่อ่าน err ตั้งแต่ route ถ้ายิง API แล้วได้ 404 แปลว่า route นั้นไม่มีอยู่จริงหรือเรายิง route นั้นผิดเอง ถ้ายิง API แล้วได้ 401 แปลว่าไม่มี token หรือ token ผิด หรือ หมดอายุ ปัญหาอยู่ที่ route ที่เช็ค auth (หรือ test ลืมส่ง auth ใน header) ถ้ายิงแล้วได้ 403 แปลว่า token ถูกแต่ role ไม่มีสิทธิ์ เช่น voter ไปยิง route ของ กกต. หรือเลือกผู้สมัครนอกเขต ปัญหาอยู่ที่ route ที่เช็คสิทธิ์หรือ business rule ถ้ายิงแล้วได้ 400 แปลว่า body ที่ส่งไปไม่ผ่าน validation เช่น nationalId checksum ผิด, password สั้นกว่า 8 ตัว หรือ district ไม่รู้จัก ปัญหาอยู่ที่ test data ที่เราใส่ หรือ validation ใน route/service ถ้ายิงแล้วได้ 409 แปลว่าไปชนข้อมูลที่มีอยู่แล้ว เช่น nationalId ซ้ำ ปัญหาอยู่ที่ test data ที่ไม่ "สด" หรือรันซ้ำโดยไม่ reset ถ้ายิงแล้วได้ 500 แปลว่ามี error หลุดจากฝั่ง server ต้องไปอ่าน log ของ SUT ด้วย docker compose logs -f app ว่า throw ที่บรรทัดไหน ถ้ายิงแล้วได้ 200 (คือ status ถูก) แต่ข้อมูลที่ตอบกลับไม่ตรงกับที่ assert อันนี้ต้องแยกว่าเป็น bug ที่ service/repository หรือที่ test data โดย query database ตรงๆ ว่าในตาราง candidates กับ parties มีข้อมูลตรงกับที่ seed ไว้ไหม ถ้า database ถูกแต่ API ตอบผิด = bug ในโค้ดจริง (route/service/repository) แต่ถ้า database ไม่มีข้อมูลหรือเขตผิด = bug ที่ test data/seed ของเรา ถ้าจะให้ชี้ชัดว่า test data หรือโค้ด ให้รัน component test app/test/integration/elections.test.ts เพราะมันสร้าง data เองแบบ deterministic ถ้า component test ผ่าน แต่ e2e แดง คือ bug อยู่ที่ environment/test data ของ e2e (เช่นไม่ได้รัน context e2e-exercise) ถ้า component test แดงด้วย คือ bug อยู่ที่ตัวโค้ด SUT จริง ส่วนจะแยกว่า bug อยู่ที่ route, service หรือ repository ให้ดูว่า endpoint นั้นเดินผ่านชั้นไหน ในเคสนี้ /me/candidates เขียน raw SQL อยู่ใน route ตรงๆ (src/routes/voteRoutes.ts:8) ไม่เรียก repository เลย เพราะฉะนั้นถ้า component test แดงที่ endpoint นี้ bug จะอยู่ที่ route

2. ทำไม e2e test ควรมี **น้อย** เมื่อเทียบกับ unit test? อะไรบ้างที่ e2e test เท่านั้นจับได้?
ตอบ. e2e test ควรมีน้อยกว่า unit test เพราะรันช้า ต้องพึ่งพาหลายส่วน เช่น Docker, Database, Liquibase, API และ test data อีกทั้งเมื่อ fail จะวิเคราะห์สาเหตุยากและดูแลรักษายาก unit test จึงควรเลือกทดสอบเฉพาะ user journey ที่สำคัญทางธุรกิจ ส่วน unit uest เหมาะกับการตรวจ business rule, validation และ edge case จำนวนมาก
e2e test มีความสำคัญเพราะยืนยันได้ว่าระบบทุกส่วนทำงานร่วมกันจริงในสภาพแวดล้อมที่ใกล้เคียงการใช้งานจริง เช่น Docker image เปิดได้, API เชื่อม PostgreSQL ได้, Liquibase สร้าง schema และ seed data สำเร็จ, HTTP route/JWT/Authorization ทำงานข้ามหลาย request และ voter ในเขต CM-2 เห็นเฉพาะผู้สมัครของเขตตนเองได้จริง

3. inject test data ผ่าน Liquibase (SQL) กับผ่าน API ต่างกันอย่างไร? แบบไหนเสี่ยงกว่าเมื่อ schema เปลี่ยน?
ตอบ. การ inject ผ่าน Liquibase เป็นการเขียน SQL เพื่อใส่ข้อมูลลง Database โดยตรง เช่นไฟล์ 902-e2e-exercise-seed.sql ที่ใช้ INSERT INTO parties และ INSERT INTO candidates วิธีนี้รวดเร็ว ได้ข้อมูลชุดเดิมแน่นอนทุกครั้ง และไม่ต้อง Login หรือเรียก API หลายขั้นตอน จึงเหมาะกับการสร้างข้อมูลตั้งต้นสำหรับ e2e test อย่างไรก็ตาม วิธีนี้ผูกกับโครงสร้าง Database โดยตรง ผู้เขียนต้องรู้ชื่อตาราง ชื่อ column และความสัมพันธ์ของข้อมูล อีกทั้งการใส่ข้อมูลด้วย SQL จะไม่ผ่าน validation, authorization และ business rule ที่อยู่ใน API
ส่วนการ inject ผ่าน API คือการสร้างข้อมูลเหมือนการใช้งานจริง เช่น Login เป็น กกต. แล้วเรียก POST /parties เพื่อสร้างพรรค และ POST /districts/:id/candidates เพื่อสร้างผู้สมัคร วิธีนี้ทำให้ข้อมูลผ่าน validation, role authorization และ business rule ของระบบ จึงใกล้เคียงการใช้งานจริงมากกว่า แต่จะช้ากว่าและมี dependency มากกว่าเพราะต้องมีบัญชี กกต. ต้อง Login ได้ และต้องสร้างข้อมูลตามลำดับ หาก API หรือสิทธิ์ของ กกต. มีปัญหา การเตรียมข้อมูลก็จะทำไม่ได้
เมื่อ schema ของ Database เปลี่ยน วิธี Liquibase/SQL มีความเสี่ยงมากกว่า เพราะ SQL อ้างอิงชื่อตาราง, column, constraint และความสัมพันธ์โดยตรง หากมีการเปลี่ยนชื่อ column, เพิ่ม field ที่บังคับกรอก หรือเปลี่ยนความสัมพันธ์ของตาราง ไฟล์ seed SQL อาจรันไม่ผ่านและต้องแก้ไขตาม schema ใหม่ ส่วนการ inject ผ่าน API จะได้รับผลกระทบน้อยกว่า หาก API contract ยังเหมือนเดิม เพราะแอปพลิเคชันสามารถจัดการการเปลี่ยนแปลงภายใน Database ได้เอง อย่างไรก็ตาม หาก API contract หรือ business rule เปลี่ยน Test ที่เตรียมข้อมูลผ่าน API ก็ต้องปรับเช่นกัน
